## 现象

耀创工坊专属 API 配置窗口原先只支持 `gpt-image-2`。用户已经在同一 API 服务中为自己的 Key 开通“香蕉生图”分组，但软件没有可选择的对应图片模型，无法通过现有 API 流程调用该能力。

## 根因

中转传输层、连接检查、批量任务和配置 UI 都把 `gpt-image-2` 当作唯一固定模型。香蕉分组实际开放的是 Gemini 原生图片模型，并不使用 `/v1/images/edits` 的 multipart 协议，因此只替换模型字符串无法工作。

## 解决方式

- 在同一个“配置耀创工坊专属 API”窗口增加两个受控选项：
  - `标准图片`：`gpt-image-2`
  - `香蕉生图`：`gemini-3.1-flash-image-preview`
- 模型选择保存到现有设置字段，弹窗摘要和主任务面板同步显示当前选择。
- 标准图片继续使用现有 `/v1/images/edits` multipart 流程。
- 香蕉生图使用原生 Gemini `streamGenerateContent?alt=sse`：提示词和全部附件通过 `contents[].parts[]` 发送，要求 `TEXT` 与 `IMAGE` 响应，并从流式事件的 `candidates[].content.parts[].inlineData` 读取图片。
- 连接检查按当前选中的精确模型查询 `/v1/models`，模型未开放时明确阻止任务；两个模型之间不静默切换。
- Key 继续只存在于当前运行内存，勾选“记住本机”时才由 Electron `safeStorage` 加密保存。源码、设置、项目、断点、日志和测试均不写入真实 Key。

## 经验教训

- 同一 API 站点下的不同分组不代表使用同一图片协议，必须先确认精确模型和请求格式。
- 模型选择必须贯穿能力检查、请求构造、状态展示和批量任务，不能只做 UI 开关。
- 生成请求不做自动重提；连接中断时不能通过重复付费 POST 掩盖问题。
- 用户在聊天中暴露过 Key，完成手测后应在服务端撤销并创建新 Key。

## 真实手测连接重置热修

### 现象与证据

- Hale 使用已安装 `1.2.2` 执行香蕉生图两张任务时，任务 1 在约 39 秒后于结果正文接收阶段报 `ECONNRESET`，任务 2 随后约 2 秒内同样失败，保存 `0/2`。
- 同一 Key、同一模型和同一请求结构稍后重新执行时，两张均成功保存，单张结果接收约 44–65 秒。因此 Key、模型分组和请求协议并非持续无效，故障属于长响应连接的间歇性中断。

### 根因

- 旧实现等待整个非流式 JSON 和大块 Base64 完整到达后才解析图片；连接在末尾断开时，即使图片数据已经到达，也会因 `arrayBuffer()` 整体失败而全部丢失。
- 连接失败后仍保留原网络通道为活动通道，下一任务可能立即复用同一条异常连接，解释了第二张在两秒内连续失败。

### 修复

- 改用服务端已支持的 Gemini SSE 流式端点，逐事件读取并在完整图片事件到达时立即保留结果。
- 图片已完整到达、但连接在结束标记前断开时，使用已收到的图片继续保存。
- 图片到达前断线时不自动重提付费 POST；当前任务明确失败，以避免重复扣费或产生重复图片。
- 连接级失败会使后续任务切换到另一条现有网络通道，并清除当前会话的连接能力缓存；不会重试刚才失败的付费任务。

- 大型内联图片响应不应等完整正文结束后才一次性解析，流式事件可以缩短连接空闲窗口并保留已经完整到达的结果。
