# 像锚：从一个车主的问题，到一套可复盘的 AI 视觉生产工作流

> 讲述口径：这是我基于品质车生活业务经验做的独立产品。2025 年开始积累问题和方案，2026 年 7 月离职后集中产品化。下面的业务场景是对我工作中反复遇到的一类问题的归纳，不把某个未经记录的客户、订单或业绩编成真实案例；产品能力以当前源码和维护记录为边界。

## 一、先说人和业务，不先说技术栈

我叫李佳康。早期在中泰证券做全栈工程，后来在上海三快在线科技有限公司参与品质车生活相关业务，工作从前端和业务系统逐步延伸到 AI Agent 架构、RAG、多模态素材、模型网关和数据治理。业务包括隐形车衣、个性化改色、轻度改装、精细车美等，用户会从线上内容进入咨询、预约到店和线下服务。我的简历里有车主售前导购、车生活 AI 基础设施、矩阵营销创作和车主案例资产等项目；像锚不是把这些内部系统搬出来，而是我离职后围绕其中一个反复出现的工作问题做的独立桌面工具。

这类业务和普通低客单商品不一样。一个车主考虑贴车衣或改色，往往会问很多细节：某个颜色放在自己的车型上会怎样，光线下会不会偏色，车身线条是否还清楚，哪些地方能改、哪些地方不能改。对顾问来说，一张图只是沟通起点，不能替代材质、报价、门店能力和施工风险的说明；对内容团队来说，做出“好看但不可信”的图也很容易带来后面的返工。

我开始做这个软件，想解决的不是“再做一个出图按钮”，而是让业务要求在生成前说清楚，生成中可追踪，生成后能判断哪里对、哪里错，并让下一次少犯同一种错。

## 二、一个能讲清楚的典型场景

假设内容同事要为一组车生活案例准备社交媒体宣传图。原图里有车辆、门店环境和一位已授权出镜的人物，运营希望保持车辆与场景不动，只调整人物的指定区域或穿搭，让同一组素材适配不同内容主题。过去的做法可能是把几张图丢进模型，再用一段长提示词解释。结果常见两种：人物改对了，但车身细节或背景跟着变了；或者画面很漂亮，却与原图和参考穿搭对不上。下一位同事接手时，还得重新翻聊天记录猜上一轮是怎么做的。

像锚把这件事拆成可以核对的步骤：先确认使用授权，导入原图和参考图，明确哪一块允许编辑；再根据原图理解生成提示词，由人复核后发送；服务返回结果后保存文件、评分、写备注，不满意就针对具体问题生成下一轮修正提示词。一个批次被网页验证、限流或网络中断打断时，系统保留任务状态和已经保存的图片，避免把已成功的任务再发一次。

这个场景来自品质车生活的工作语境，也与软件当前的**授权人像区域编辑**能力对应。它还具备穿搭参考、姿势、图片生成和结果归档能力。它不是一套完整的车身改色仿真或门店交易系统。面试时我会主动讲清这个差别，因为产品当前能证明的是“受约束的视觉工作流”，不是对任何车型和材质的真实施工效果担保。

## 四、离职后的心路历程

被裁员以后，我最先感到的不是“终于有时间做产品”，而是失去了团队、业务系统和协作链路的支撑。以前一个需求能通过产品、运营、销售、施工团队一起厘清；独立做产品时，问题定义、界面、工程、测试和使用反馈都得自己扛。那段时间我需要证明的不只是会写 Agent 架构图，而是离开一个大组织后，还能不能把一个模糊痛点做成别人能实际操作、出了错能找到原因的软件。

一开始我也容易被“效果图一出来就很惊艳”吸引。但真正做批量时会碰到更难看的问题：网页点了发送却没收到、模型返回的还是白板占位图、请求状态不清楚却可能再次扣费、结果保存了但进度没记住、换一张参考图后旧提示词还挂在界面上。这些问题不适合写在宣传页上，却决定了软件能不能进入真实工作流。我后来花了很多精力在状态、证据、断点、数据不丢和错误提示上。

这也改变了我对“AI 产品”的理解。模型能力很重要，但用户真正信任的是：它知道自己被授权改哪里，知道什么时候不能继续，知道哪些结果已经保存，知道它为什么给出下一轮建议。一个生成结果要进入业务，必须有人的判断和回退通道。对我来说，这才是从演示走向产品的分界线。

这段经历也让我更想回到有真实场景的业务里继续做 AI。独立产品能证明我能把一条链路从头做到尾，但品质车生活这类本地服务的真正难题，仍要和内容、顾问、门店、履约、数据团队一起解决。

## 五、软件现在的闭环具体在哪里

1. **输入有来源**：主图、目标参考图、穿搭参考图和描述分别管理。用户能看到本轮到底拿了哪些素材，避免“模型自己猜”。
2. **编辑有边界**：红圈限定可编辑区域；提示词强调哪些地方不改。对于授权人像编辑，还可选遮挡处理。区域、素材与提示词之间保持状态一致。
3. **执行有快照**：发出任务时冻结模型、附件、提示词和数量。网页路线需要确认附件和消息真正被接收；API 路线要处理付费请求、下载和保存的不同状态。
4. **异常可恢复**：批量任务中断后，从缺失任务继续。网页遇到人工验证会暂停；付费 POST 是否成功不明时进入待确认，不自动重复扣费。
5. **结果可复盘**：图片被保存或归档后，可评分、备注、标记问题，并生成二次修正提示词。相机质感处理生成独立副本，原结果保留。

这里的“闭环”目前是**单个制作任务的工作流闭环**。它让人能根据结果改下一轮，也为以后积累案例提供结构化入口；它还没有把评分自动变成模型权重更新，也没有证明能够提高咨询或到店转化。

## 六、为什么要往“AI 自进化”走，以及怎样走

我在原来的业务项目里做过案例沉淀、检索、Agent 编排、评测、人工复核和灰度回流，所以会自然地问：一个工具能否从“每次都靠操作者从头写提示词”，发展到“在受控条件下复用被证明有效的经验”？这个方向可以称为自进化，但不能理解成模型自己改自己、自己发布自己。

我设想的最小路径如下：

1. **先留对数据**：把任务场景、授权状态、素材类型、编辑边界、提示词版本、结果评分和失败原因关联起来。图片和人脸数据默认留在本地；要跨项目复用，先做授权、脱敏与可撤回设计。
2. **再定义可比的案例**：比如“保持原构图的人像局部编辑”“穿搭参考优先”“光影一致性”“车型视觉素材的场景约束”。每一类都有人工审核的好例、坏例和失败原因，不能把单个高分当成通用规则。
3. **让系统提建议**：检索相近案例，给出参考提示词和编辑约束，并说明建议来自哪一类历史案例。人可以接受、改写或拒绝。
4. **用评测限制演进**：建立固定样本集，测编辑区域外变化、身份/车型一致性、素材引用正确率、人工返工率、单任务成本和失败恢复率。高风险样本人工复核，版本可回滚。
5. **最后才谈策略发布**：当新模板或策略在离线评测和小范围使用中稳定优于旧版，再灰度发布。模型微调只有在数据合法、量足够、成本收益明确时才考虑；否则优先改检索、提示词和流程。

当前仓库已有结果评分、备注、二次修正和任务记录这些入口；**案例检索驱动的自动策略升级、在线学习、模型微调和业务转化评测尚未作为产品能力上线**。这个边界说清楚，才有讨论下一步的基础。

## 七、我为什么觉得它适合美团方向

我不是说像锚已经接入美团业务，也不是说它可以直接复制到所有类目。我看重的是美团本地生活里“线上决策影响线下履约”的特点。品质车生活恰好是一个高决策成本的例子：用户看内容、提问、比较、预约，到店后才真正完成服务。AI 图像如果只管曝光，不管事实和履约，可能增加误导；如果能帮助顾问和车主把需求说准确，并把真实案例反馈回来，就可能减少沟通往返和内容返工。

要让这个方向有业务价值，我会先选一个窄场景试点，比如经过授权的车生活案例宣传图中的人物素材辅助制作。验收不看“日生成多少张”，而看：内容审核通过率、制作耗时、返工轮数、顾问是否愿意使用、咨询时需求是否更清楚、预约到店后的预期偏差有没有下降。这些指标要与业务团队共同定义并做对照，不能拿我现在的个人项目推断出转化提升。

如果公司已有内容平台、资产库、模型网关和实验系统，我不会让一个 Electron 桌面工具长期承载全部平台能力。它可以先作为生产端验证工作流；证明确实有价值后，把案例、评测和策略管理沉到公司平台，和现有系统对接。桌面形态适合快速处理本地素材、保护敏感文件、给操作者明确的文件和任务状态；组织级协作则需要服务端权限、审计与版本治理。

## 八、面试官可能追问的问题



### 1. 你为什么做这个软件？是为了找工作临时包装的吗？

我在 2025 年做品质车生活业务时已经反复遇到内容生产与案例回流的断点。离职后我选了其中边界最清晰、自己能独立做出完整链路的一段，集中做成产品。当前版本的投入点不是一页漂亮演示，而是断点恢复、请求状态、结果落盘、素材状态同步和错误处理；维护记录可以看具体过程。

### 2. 它和你简历中的公司项目是什么关系？

业务问题、方法和技术判断来自工作经历；像锚是离职后独立实现的产品。我不把公司的车主数据、案例、内部服务或业务指标说成这个仓库的资产。简历中的 RAG、Agent、网关、评测经验解释了我为什么这样设计下一步，但不等于这些企业能力已全部在软件里复刻。

### 3. 为什么从 2025 年算起，代码记录却主要在 2026 年？

2025 年算问题定义与前期探索，2026 年 7 月离职后才集中产品化。现在这份仓库也是后续交付形成的源码副本，提交历史不能代表全部工作历史。我会按“业务探索”和“软件实现”两个阶段讲，不混用。

### 4. 产品的独特性是什么？为什么不用通用 AI 网页？

通用网页解决的是单次生成；这个工具把授权、编辑区域、参考图、提示词、模型选择、批量任务、异常恢复、文件保存和结果复盘放进一条可检查流程。优势如果成立，应体现为更少的返工、更低的重复提交成本和更清楚的责任边界，而不是声称模型比通用平台更强。

### 5. “自进化”现在到底实现了多少？

实现了结构化输入、任务状态、结果归档、评分备注和二次修正。尚未实现基于历史案例的自动检索建议、自动评测门禁、策略灰度发布或权重微调。我把它定义为产品路线，而非现状宣传。

### 6. 你怎么证明它对业务有用？

先做小场景试点：相同车型/素材质量下比较人工制作时间、结果审核通过率、返工次数与顾问使用意愿，再追踪咨询质量和到店后的预期偏差。现在没有这组对照数据，所以不会报转化提升百分比。

### 7. 人像与车主数据怎样处理？

只处理获得授权的素材。项目、结果和浏览器登录资料在本机管理；网页或 API 生成会把本轮素材发送给用户选择的服务商，需要使用者确认其数据处理与计费规则。API Key 不写进普通项目文件。组织内使用还需要补齐角色权限、审计、保留期限和删除机制。

### 8. 网页自动化不稳定，为什么还做？

因为部分用户先有网页会员和现成工作习惯，网页路线能验证工作流。但它受页面变化、登录验证、限流影响，所以软件会暂停、保留断点，也提供用户自配 API 路线。网页自动化是现阶段的接入方式，不应成为未来企业级系统的唯一基础。

### 9. 你最有代表性的工程取舍是什么？

把“点击发送”和“服务端已接收”分开；把“模型返回”和“图片已通过校验并落盘”分开；把“生成请求失败”和“生成状态不明”分开。尤其是付费 API，状态不明不能自动重发。这些取舍不花哨，但直接关系到重复扣费、数据丢失和用户信任。

### 10. 你一个人能做多少，团队里又能带来什么？

我能独立从业务问题、界面、Electron/React 实现、模型接入、状态设计到验证交付，把一条小链路闭合。更大规模的价值在跨团队：跟内容、销售、门店、法务和平台工程一起定义样本、事实边界、风险、评测与上线门槛。这与我过去的业务落地经历是一致的。

> 我在品质车生活业务里做过售前导购、案例资产和多业务 Agent。车衣、改色这类服务，用户线上看到内容后还要咨询、预约、到店，图做得漂亮却与实物和施工边界不一致，后面就会付出沟通和信任成本。我因此一直关心：AI 生成之前，能不能把允许改哪里、参考什么、哪些事实不能变说清楚；生成之后，能不能知道哪个版本有效，失败了怎么继续。2025 年我在业务项目中积累问题和方法，2026 年离职后把它做成独立桌面软件。第一阶段先打通原图、参考图、红圈、提示词、生成与归档，后来在真实使用和测试里发现，更难的是网页验证、重复发送、付费请求状态不明、白板图误保存，所以又补了任务快照、断点和校验。当前软件已经能支持人来判断和修正一轮结果，但还没有自动学习。我想继续往“审核后的案例进入检索，策略先评测再灰度”的方向做，最终看内容返工、顾问沟通和到店预期是否真的改善。



## 十、我会主动承认的边界

- 软件当前核心是授权人像区域编辑与视觉工作流；不是车身改色物理仿真、施工报价或门店履约系统。
- 2025 年是业务问题与方案积累；可核验的独立软件版本主要在 2026 年下半年。
- 结果评分与备注已具备；自动案例检索、自动策略升级、模型微调和线上业务转化闭环仍是规划。
- Gemini 网页入口目前不可选；网页服务的页面变化和平台限制无法由本地工具消除。
- macOS 源码有适配工作，但签名、公证和目标机器上的完整发布验收要单独确认。
- 公开的仓库不能证明公司业务指标或客户订单；涉及前雇主的内部数据、具体客户和效果数值，应以本人有权披露且可核验的材料为准。
