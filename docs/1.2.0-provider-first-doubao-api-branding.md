# 1.2.0 制作通道前置、豆包网页分析与 API 品牌收敛

日期：2026-08-24

## 问题现象

1. API 做图通道原本位于右侧执行区，用户在点击 AI 分析和网感姿势之前不能直观看到“分析来源”和“最终做图方式”的组合。
2. 选择 API 做图后，AI 分析和网感姿势仍缺少可独立使用的网页来源，容易让用户误以为分析也必须走图片生成 API。
3. API 配置、状态和错误文案仍出现服务商或“中转站”名称，不符合耀创工坊统一产品身份。

## 真实根因

- 分析 Provider 保存在设置中，生成 Provider 保存在工作流状态中，但界面入口分散，没有显式呈现两者组成的制作路线。
- 网感姿势 IPC 过去默认绑定 ChatGPT；Gemini 与豆包网页没有完整的 Provider 分发。
- 传输层名称曾直接进入主进程状态和渲染器文案，内部协议实现与用户可见产品名称没有分离。

## 解决方式

- 在“原图理解”顶部增加制作通道区，先选择最终做图通道 `ChatGPT / Gemini / API`，再选择分析来源 `ChatGPT / Gemini / 豆包网页`。
- API 做图与网页分析完全解耦。用户可先选择“API + 豆包网页”，再执行 AI 分析、8 条网感姿势、一键生成提示词和 API 正式做图。
- 新增独立豆包网页自动化适配器和专属标签页：只处理页面就绪、附件上传、提示词发送、发送确认和结构化回复，不扫描或点击豆包模型菜单。
- AI 分析、网感姿势和正式做图继续共享现有页面操作互斥；发送状态不确定时停止，不重复点击发送。
- Gemini 网感姿势补齐独立分发，避免界面允许选择但主进程仍固定走 ChatGPT。
- 用户可见文案统一为“API”或“耀创工坊专属 API”。连接成功状态为“API 已连接，当前分组已开放 gpt-image-2。”；源码与 UI 验收脚本中不再出现旧服务商显示名。
- API Key 仍由用户自行填写；默认仅当前运行有效，选择记住本机时使用 Electron `safeStorage`，不写入项目、普通设置、断点、日志或安装包。

## 验证边界与经验教训

- 豆包网页链路已通过 TDD、IPC、页面行为夹具和打包应用验证；本轮没有使用真实豆包账号发送消息，因此登录状态、地区限制和网页后续改版仍需 Hale 最小手测。
- 持久 `js_repl` 在当前环境不可用，视觉检查由仓库内真实 Electron/Playwright 脚本完成，未把静态源码断言冒充真实界面验证。
- 生成通道和分析来源是两个正交选择，UI 必须先把路线说明白，再让用户开始分析；内部传输实现名称不应泄漏到产品文案。
