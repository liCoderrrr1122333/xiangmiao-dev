# 耀创工坊 0.3.1 模型菜单适配记录

## 现象

- ChatGPT 网页已经在输入框右侧显示“高”模式按钮和模型菜单，但耀创工坊提示“当前 ChatGPT 页面没有显示模型选择器”。
- 用户无法在耀创工坊中看到当前账号实际可用的模型。
- Image 2.0 提示词区域存在“只编辑红圈内、红圈外锁定、保持原图光影、提示词已就绪”等重复状态标签。

## 根因

- ChatGPT 新版页面把模型选择器改成两级 Radix 菜单：输入框中的“高”先打开模式菜单，再由 `GPT-5.6 Sol` 子菜单打开实际模型列表。
- 旧实现只识别带有 `model selector` 等明确语义的一级按钮，因此有意避开个人资料菜单时也漏掉了新版嵌套入口。
- 新版 Radix 菜单不响应普通 `HTMLElement.click()`；需要完整的指针与鼠标事件序列，子菜单还需要悬停事件。
- 重复状态标签只承担说明作用，没有参与提示词约束或发送逻辑。

## 解决方式

- 保留原有独立模型选择器识别路径，新增严格受限的编辑器嵌套菜单探测路径。
- 仅探测编辑器内部、可见、可用的 `composer-pill` 或模式按钮；继续排除侧栏、头像、账号和个人资料菜单。
- 只有在一级菜单出现模型格式的子菜单入口，且二级菜单出现实际模型项时才判定成功。
- 模型项采用结构与格式共同校验，识别 `GPT-5.6 Sol`、`GPT-5.5`、`GPT-5.3`、`o3`，不把“高”“中”“极速 5.5”当成模型。
- 使用 `pointerdown/mousedown/pointerup/mouseup/click` 触发菜单，使用 `pointerover/mouseover/pointermove/mousemove` 打开子菜单。
- 指定模型后重新打开菜单并检查 `aria-checked` / `data-state=checked`，未确认时停止本轮发送，不静默回退。
- 首次启动时若输入框已经出现、模型菜单仍在水合，冷启动最多探测十次，已有近期登录确认时最多快速探测三次；整体受界面 60 秒超时保护。
- 冷启动且没有近期登录确认时，“刷新模型”会先在后台完成一次登录与页面健康复核；正常启动已复核过则直接跳过，不增加热路径耗时。
- 删除提示词面板中的四条重复状态标签及对应死样式，不修改提示词正文里的红圈外保护规则。

## 验证结果

- `npm test`：82/82 通过。
- `npm run verify:chrome`：通过；本地管道、固定端口后备、标签页隔离、隐藏与显示、窗口恢复均正常。
- 真实登录账号读取成功：`GPT-5.6 Sol`、`GPT-5.5`、`GPT-5.3`、`o3`。
- 当前模型识别成功：`GPT-5.6 Sol`。
- 正式安装版冷启动的延迟水合时序已复现；采用冷热分路的有界复查，不进行无限轮询，热启动首次成功后立即返回。
- 进一步确认模型菜单依赖会话复核后的页面水合；模型刷新冷路径现在先完成后台登录复核，再开始菜单探测。
- 后台模型切换实测：`GPT-5.6 Sol` 切换至 `GPT-5.5` 后读取到选中态，再恢复至 `GPT-5.6 Sol`。
- 未上传附件、未发送提示词、未消耗图片生成额度。
- UI 实测确认四条重复标签均已移除，提示词保护规则仍由 `operationGuideBuilder` 保留。

## 经验教训

- 模型选择不能只依赖按钮文案；ChatGPT 会按账号、语言和灰度版本改变菜单层级。
- 对动态菜单必须先验证结构，再读取内容，不能放宽为“任何包含 GPT 的菜单”。
- Radix 组件的 DOM `click()` 不等于真实用户操作，自动化需要覆盖实际指针事件序列。
- “输入框可用”不代表输入框旁的异步菜单已经完成水合；首次探测需要一次短延迟复查，但必须限制次数。
- 任何模型切换都必须二次确认选中态；读取失败和切换失败必须停止发送并给出可读原因。
