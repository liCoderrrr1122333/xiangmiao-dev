日期：2026-08-09

## 现象

1. Gemini 能选模型和上传图片，但右侧发送箭头不稳定，AI 分析有时只回填部分文本。
2. 旧代码尝试在“上传和工具”菜单内点击“制作图片”，但真实新页面的该菜单只有上传项。
3. 输入框清空或页面显示忙碌时，旧接收判定可能误报成功；实际新会话没有持久化到 `/app/<会话ID>`。
4. Gemini 成功生成图片后，结果地址是已渲染的 `blob:` URL。页面 `fetch` 失败，HTTP 会话下载备选也无法处理 `blob:`，导致“已出图但无法保存”。
5. 结果描述中出现 `icon` 或 `logo` 时，旧语义过滤会把合法生成结果当成界面图标排除。

## 根因

- Gemini 页面 DOM 已更新，旧“制作图片”菜单前置步骤不再是可依赖契约。Google 当前官方帮助流程是上传参考图后直接提交生成或编辑指令。
- `commonDomScript` 同时统计了 `user-query` 及其多层 class 后代，并优先使用可能为空的 `response-selection-panel`，消息数不是真实顶层消息数。
- 接收策略把 `busy=true` 单独当成成功证据，没有对新对话 URL 做持久化确认。
- 下载器只有页面 fetch 和 HTTP(S) `session.fetch` 两层，缺少从已渲染 `<img>` 读取原始像素的路径。
- 候选筛选把内容语义与 UI 资产语义混在一起；用户本来就可能生成应用图标或 Logo。

## 解决方式

- Gemini 与 ChatGPT 保持同样的主流水线：新对话 -> 精确模型确认 -> 上传及稳定预览确认 -> 提示词快照 -> 最终发送门禁 -> CDP 可信按钮点击 -> 接收确认 -> 新结果确认 -> 三次本地保存重试。
- 图片生成准备改为 `direct-prompt`；提示词以“请直接生成一张新图片”开头，不再依赖不存在的菜单。
- 只统计顶层 `user-query` / `model-response`；只在可观察证据连续两轮稳定后确认接收。从 `/app` 新对话发送时，必须等 URL 进入真实会话。
- “只是语言模型、不具备能力”类明确拒绝立即归类为不可重发的 `generation-failed`，不再空等五分钟。
- `downloadGeminiImage` 优先在本轮 `model-response` 内定位已加载结果图，以 `naturalWidth/naturalHeight` 读取原始像素为 PNG；若 Canvas 被跨域污染，仍保留页面 fetch 和认证 HTTP 会话备选。
- 结果候选仍必须是本轮新 source、可见且至少 `256x256`，但不再以 `icon/logo` 等用户内容词误杀。

## 残余风险

- Gemini 是外部动态网页，DOM、模型能力、账号额度、地区可用性和网络状态仍可能变化；代码保证可观察确认、有界重试、断点和可读失败，不能保证外部服务永不失败。
- 当前源码热修复尚未进入安装包。正式发布前必须重新打包、扫描、升级安装并在已安装版再跑真实 ChatGPT/Gemini 闭环。
- 同一 `ChatGPT-Chrome` 登录目录不能被已安装版和源码验证进程同时持有；真实验证前必须正常退出托盘驻留进程。

## 经验教训

1. “点击返回成功”不等于 Provider 已接收；新消息、会话 URL 和结果基线必须交叉确认。
2. 官方产品流程发生变化时，应删除已失效的必选前置步骤，不能让旧菜单选择器决定主流水线成败。
3. `blob:` 是网页生成结果的正常形式；已渲染图像的原像素读取应优先于重新请求短命 URL。
4. 内容过滤不能用 `icon/logo/profile` 等正常创作词做粗糙黑名单；应依赖消息所属、发送前 source 基线、可见尺寸和稳定时间。
5. 真实测试必须区分 Provider 失败、浏览器资料占用和本地保存失败，否则会在错误边界修复问题。
