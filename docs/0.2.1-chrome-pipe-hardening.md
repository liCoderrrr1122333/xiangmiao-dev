# 耀创工坊 0.2.1 专属 Chrome 管道加固记录

## 问题现象

- 部分用户的 Chrome 或 Edge 可以正常打开，但耀创工坊提示“专属 Chrome 窗口未能打开”。
- “查看窗口”偶发长时间无反馈，或软件返回成功但用户没有看到可操作窗口。
- Google 登录页已经显示，邮箱也已填写，但用户反馈“下一步”无反应。
- “检查登录”在用户仍停留于 Google OAuth 页面时仍会执行 ChatGPT 页面探测。

## 根因

1. 0.1.10 的自动化控制只依赖 `127.0.0.1` 固定调试端口。普通浏览器能打开，只能证明浏览器程序可运行，不能证明本地调试端口可绑定和连接。
2. 原先的端口分配存在时间窗口：软件先申请空闲端口、释放端口，再启动 Chrome 绑定。VPN、安全软件、端口保留或其他进程可能在两步之间影响绑定。
3. Chrome 与 Edge 原先共用一个自动化用户目录。一个浏览器留下的锁文件或不兼容配置可能影响另一个浏览器兜底。
4. 原生窗口显示操作是异步的，渲染层在 Windows 尚未确认窗口可见时就可能收到“已显示”。
5. Google OAuth 页面仍会进入通用登录探测循环。虽然没有自动填写账号，但不应在用户人工登录期间持续注入 ChatGPT 探测脚本。
6. 实测 `--remote-debugging-port=0` 虽能避开端口竞争，但会使 Chrome 暴露 `navigator.webdriver=true`，可能触发 Google 的自动化差异路径，因此不能作为正式方案。

## 解决方式

- 增加 `playwright-core`，默认通过 Chrome DevTools 本地管道连接，不再依赖 TCP 端口。
- 管道模式移除 `--enable-automation`，同时使用 `--disable-blink-features=AutomationControlled`。真实 Google 登录页验证 `navigator.webdriver=false`。
- 保留原固定端口实现作为第二通道；管道启动失败时自动切换，不降低旧机器兼容性。
- Chrome 与 Edge 使用独立持久化目录。Chrome 登录数据继续沿用原目录，Edge 使用单独的 `-Edge` 目录。
- 浏览器查找同时覆盖标准安装路径、当前用户安装路径、Windows App Paths 注册表和 `PATH`。
- “查看窗口”必须等待 Windows 原生窗口句柄确认；首次唤出失败时，自动以可见模式重启一次并再次确认。
- 原生窗口恢复会校验标题栏和可见区域。窗口在屏幕外、过小或标题栏不可拖动时自动居中。
- Google OAuth 页面进入人工登录保护态：不刷新、不执行 ChatGPT 登录探测、不自动隐藏，并保持“查看窗口”和“检查登录”可恢复。
- 页面加载以 DOM 可交互为完成信号，去掉重复导航，缩短首次启动等待。
- 启动诊断新增传输方式、浏览器路径、独立配置目录、端口后备结果、进程退出状态和窗口恢复结果。

## 经验教训

- 浏览器可启动、页面可联网和自动化通道可连接是三种不同健康状态，不能用一个检查代替另外两个。
- 重试必须切换失败机制，而不是重复同一种启动方式。
- OAuth 页面属于人工安全边界，自动化只能负责打开、保持和恢复窗口，不能持续探测或替用户操作账号。
- Windows GUI 操作不能只更新内存状态，必须等待真实窗口句柄反馈。
- 端口 0 能解决连接问题，但会改变浏览器自动化标志；任何启动参数变更都要同时验证 Google 登录行为。

## 外部边界

耀创工坊可以保证窗口启动、恢复和软件内部状态流转，但无法保证 Google、OpenAI、VPN 节点或用户网络始终可用。若 Google 页面自身长期停留“正在加载”，应切换可访问 Google 与 ChatGPT 的网络节点后重试；软件不会绕过第三方登录安全策略。
