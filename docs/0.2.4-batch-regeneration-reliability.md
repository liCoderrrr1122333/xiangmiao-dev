# 耀创工坊 0.2.4 连续批量再生成加固记录

## 问题现象

- 用户连续生成并保存 5 张图片后，更换人脸参考图。
- 界面仍显示“重新生成 5 张”，但按钮变灰且无法再次点击。
- 用户无法直接知道是哪一个发送前置条件没有恢复。

## Graphify 调用链

本次对 `src` 中 37 个代码文件执行 AST 图谱提取，共得到 491 个节点和 1365 条关系。相关调用链为：

1. `ReferenceImagePanel` 读取文件并更新 `projectStore.referenceImages`。
2. `App` 调用 `buildSendChecklist` 生成 `canSend`。
3. 生成按钮原先在 `canSend=false` 时直接设置原生 `disabled`。
4. `sendToChatGPT` 通过 preload IPC 调用 `send:create-package`。
5. 主进程 `automateChatGptBatch` 使用提示词、数量、目标尺寸和所有附件内容生成 SHA-256 任务键。
6. 新参考图会产生新任务键，因此不会错误沿用上一批已经完成的检查点。

## 根因

### 根因一：参考图文件输入没有复位

隐藏的文件输入在完成上传后保留了上一次选择值。删除旧参考图后，如果再次选择同名文件，Chromium 可能不会再次触发 `change`，导致界面看起来完成了操作，但项目状态仍没有参考图，`canSend` 因此保持 `false`。

### 根因二：按钮无声禁用

生成按钮直接使用 `disabled={!canSend}`。前置条件异常时，用户既不能再次生成，也不能点击按钮获得缺失条件说明，表现为“按钮坏了”。

### 稳定性缺口：前端只依赖长时间 IPC 返回解除忙碌

正常情况下 `sendToChatGPT` 的 `finally` 会恢复按钮，但主进程没有独立的批量运行生命周期事件。如果渲染进程错过长时间 IPC 的最终响应，界面缺少第二条解除忙碌的路径。

## 解决方式

- 参考图选择后立即复制 `FileList` 并清空原生输入值，保证同名文件可以连续选择。
- 非运行状态下，生成按钮保持可点击；条件不足时给出主图、红圈、参考图、提示词或衣物提示词的具体恢复说明。
- 主进程为每次接受的批量任务发送带递增序号的 `running=true/false` 生命周期事件。
- 渲染进程忽略旧序号，只接受最新生命周期；收到 `running=false` 时解除生成和暂停状态。
- 保留原任务内容哈希和检查点逻辑。参考图内容发生变化时自动建立新任务，不重复提交上一批成功图片。

## 经验教训

- 文件上传控件必须在读取文件快照后清空原生值，不能依赖浏览器自动复位。
- 关键操作不能只用灰色禁用表达错误；不可执行时也必须提供可操作原因。
- 长时间 IPC 任务需要独立、可排序的生命周期信号，不能只有 Promise 最终返回这一条恢复路径。
- 是否生成新批次应由素材内容哈希决定，而不是由界面上是否已有结果决定。
