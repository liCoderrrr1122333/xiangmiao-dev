## 问题记录

### 现象

- 大显示器上主窗口仍固定为 `1500 × 940`，没有充分利用显示器工作区。
- 三栏宽度随窗口等比例分配，原图列在宽屏下增长不足。
- `1280 × 720` 低高度布局为工具条预留 `152px` 左边距，原图画布实测只有约 `361 × 344`。
- 画布像素尺寸只监听 `window.resize`，并用“面板高度减 104px”估算；卡片伸缩、系统缩放和响应式断点变化时可能不能及时同步真实可见区域。

### 根因

1. Electron 主窗口使用固定启动尺寸，没有读取鼠标所在显示器的 `workArea`。
2. 桌面三栏使用固定比例和最小宽度，宽屏剩余空间没有优先分配给原图画布。
3. 低高度工具条放在画布左侧，横向占用过大。
4. Canvas backing store 依赖外层面板的固定减法，尺寸来源与真正绘制容器不一致。

### 解决方式

- 新增纯函数窗口策略，从鼠标所在显示器获取工作区，在边界内使用约 94%～98% 的可用尺寸并居中；极小工作区自动降低最小窗口约束。
- 桌面三栏改为“原图列吸收剩余空间，原图理解与工作流列使用有界 `clamp` 宽度”。
- `1280 × 720` 等低高度场景把 11 个画布工具收进标题栏，释放原先 `152px` 的横向占用。
- 使用 `ResizeObserver` 观察 `.canvas-wrap` 的真实内容尺寸，通过 `requestAnimationFrame` 合并连续变化，并在卸载时释放 observer、window listener 和待执行帧。
- 保持现有图像坐标、缩放、拖动、红圈和蒙脸算法不变；窗口改变后仅重绘，不改项目中的原图像素尺寸或红圈原图坐标。

### 经验教训

- 桌面生产力软件的“屏幕适配”需要同时覆盖原生窗口边界、CSS 列分配和 Canvas backing store，单改媒体查询不够。
- 画布尺寸应来自真实绘制容器，不能依赖面板高度减固定常数。
- 最低正式分辨率必须进行真实交互测量；仅检查页面未溢出会漏掉“可用但过小”的问题。
- 自动化与 UI 改动应分层验证：本次没有改 ChatGPT 自动化源码，但仍回归 Chrome 传输、上传、红圈、连续生成、后期处理和安装版流程。

## 残余风险

- ChatGPT 网页结构和账号网络状态由服务端控制；本次通过了 Chrome 传输及恢复矩阵，没有使用真实账号提交一轮在线生图，避免污染用户会话与额度。
- 软件运行中把窗口拖到另一块显示器时，CSS 和 Canvas 会立即跟随窗口尺寸；为了不打断用户操作，不会强制把用户手动调整过的窗口重新铺满新显示器。
- 4K 屏幕在不同 Windows 缩放比例下会使用 Electron 的逻辑像素；当前策略已在多组逻辑分辨率和本机缩放环境验证。
