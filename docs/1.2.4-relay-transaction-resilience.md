# 耀创工坊 1.2.4 API 事务与故障恢复

## 问题现象

- 标准图片同步返回阶段出现 `UND_ERR_SOCKET`、`ECONNRESET` 或进程意外退出时，软件无法跨重启确认哪些付费任务已经提交、哪些结果已经保存。
- 图片模型连续返回 HTTP 406 时，当前批次虽然会停止，但用户立即再次点击仍可能继续向同一异常上游提交。
- 既有测试覆盖单次断流和有限重试，但缺少可作为发布门禁的批量故障注入。

## 真实根因

1. API 批次状态只存在于当前进程内存，没有在付费提交前建立持久事务记录。
2. 上游拒绝的停止决定只作用于当前 `automateRelayBatch` 调用，没有模型级短时熔断状态。
3. 中转接口没有提供可供客户端查询的服务端任务 ID 或幂等键；在请求已受理但响应中断时，客户端无法向服务端找回结果。

## 解决方式

- 新增 `relay-batch-checkpoint.json`，以原子替换方式保存当前批次。任务在付费 POST 前写为 `submitting`，图片完成原子保存后写为 `saved`。
- 任务指纹由项目、提示词、模型、目标尺寸和附件字节生成，不包含 API Key；断点不保存提示词正文、图片内容或凭据。
- 软件异常退出后，遗留的 `submitting` 会恢复为 `uncertain`，不会自动重新扣费。用户再次明确点击后，只重试缺失或待确认任务，已保存序号直接恢复并跳过。
- 标准图片和香蕉生图统一采用单次 406 策略：首个明确拒绝不自动重复付费 POST，立即对该模型打开 120 秒短时熔断；熔断期间不发送新的付费请求。
- 406 错误保留服务端返回的脱敏 `message`、`type`、`code` 和允许公开的请求 ID，便于区分模型分组、上游路由和请求内容问题；API Key 始终脱敏。
- 连接断流继续归类为 `RESULT_UNCERTAIN`；不会把网络重置当成可自动重复提交的普通失败。
- 增加 `verify:relay-resilience`，使用本地夹具执行 100 轮断流、406 恢复、熔断和崩溃恢复场景。

## 经验教训

- 付费调用的可靠性边界必须以“提交前持久化、结果不确定时不自动重交”为核心，不能只靠内存重试计数。
- HTTP 明确拒绝与连接断流不是同一类故障：前者不得自动重复付费提交，应立即短时熔断；后者必须保守地进入待确认。
- 客户端断点无法替代供应商的异步任务查询接口。若服务商以后提供任务 ID、幂等键和结果查询接口，应优先接入服务端事务能力。
