# 耀创工坊 0.4.2 一键蒙脸运行时加固记录

## 发布范围

- 基线版本：`0.4.1`。
- 修复版本：`0.4.2`。
- 保持不变：原图尺寸、红圈编辑、AI 分析、提示词、专属 Chrome、并行做图、后期处理、结果保存和用户数据格式。

## 现象

- 主图与红圈均已就绪，一键蒙脸按钮可以点击，但正式安装版无法生成面部遮挡。
- 页面只显示“未能识别实际面部，请调整红圈后重试”，容易被误判为红圈或人脸素材问题。
- 同一项目实际包含 `1920 × 2560` 主图、有效红圈和清晰人脸。

## 根因

- MediaPipe WASM 启动脚本被转换成 `blob:` URL 后动态加载。
- 应用内容安全策略只允许受信任的本地脚本和 WASM，不允许执行 `blob:` 脚本。
- Chromium 因此阻止启动脚本，控制台记录 `violates the following Content Security Policy`，识别模型从未真正启动。
- 原错误对象没有稳定落入可读错误分支，界面最终显示了通用的“未识别人脸”提示。

## 解决方式

- 改为从安装包内 `dist/face-landmarker/wasm` 直接加载受信任的本地 WASM 启动文件。
- 人脸关键点与语义分割模型继续由受限 IPC 读取为内存缓冲区，未放宽 CSP，也未增加远程资源依赖。
- 运行时启动失败时清空失败缓存，允许下一次点击重新初始化，并显示“组件加载失败”的可读提示。
- 移除 IPC 中不再需要的 WASM 文本和二进制传输，每次首次初始化少传输 `11,475,661` 字节。

## 经验教训

- 模型文件存在、构建成功和算法单元测试通过，都不能证明正式包中的 WASM 能被 CSP 允许执行。
- 浏览器侧模型功能必须在打包资源布局中做一次真实点击验证，并同时监听 CSP、页面异常和最终业务状态。
- 安全策略不应为了修复资源加载而直接放宽；优先让资源加载方式服从既有 CSP。
- 运行时启动失败与“没有识别人脸”必须使用不同提示，否则会把程序故障错误归因到用户素材。
