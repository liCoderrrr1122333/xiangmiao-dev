# 1.2.3 API 结果连接与上游拒绝热修

## 问题现象

- 标准图片批量 6 张时，任务 1-3 正常保存；任务 4 等待 123 秒后在接收同步结果时出现 `UND_ERR_SOCKET`，任务 5 又在同一路径等待 180 秒后断开，最终保存 4/6 张。
- 香蕉生图批量 2 张时，上游连续返回 `HTTP 406: openai_error`；同一配置约八分钟后重新执行可连续保存 2/2 张。

## 真实根因

- 标准图片通过 `/v1/images/edits` 等待同步结果。Node/Undici 长连接被重置后，旧实现把它当作普通失败，也没有为下一任务切换现有备用网络通道。
- 已提交请求在结果阶段断线时，服务端可能已经受理任务。旧实现将其计入普通失败，无法表达“不能安全重复提交”的事实。
- 香蕉的 406 是已经收到的 HTTP 上游拒绝，不是 DNS、代理或套接字故障。旧实现把所有非 401/403/429 状态都归为 `CONNECTION_FAILED`，继而误切代理并继续提交下一张。
- 批量层没有区分结果待确认与上游拒绝，第一处故障后仍可能继续派发，扩大同一故障窗口内的损失。

## 解决方式

- 新增 `RESULT_UNCERTAIN`：付费生成请求在结果接收阶段断线时，不自动重复提交当前任务，将其列为待确认；下一任务切换到已有备用网络通道。
- 标准图片和香蕉流式请求共用这一结果不确定规则；如果图片已经完整到达，仍优先保存图片。
- 新增 `UPSTREAM_REJECTED`：`HTTP 406` 保持直连通道，不再误判为网络错误或切换代理；香蕉生图收到明确 406 时等待 3 秒后只安全重试一次，第二次仍拒绝则停止批次。
- 批量层通过统一的小型故障决策函数处理：结果不确定只隔离当前任务并继续其他任务；鉴权、限流和上游拒绝停止派发新任务；已经发送的其他通道继续等待和保存，不被取消。
- 状态面板分别显示完成、失败、待执行和待确认数量，最终摘要说明当前任务未自动重复提交。

## 验证结果

- TDD 红灯已分别复现：标准结果断线未切换通道、香蕉 406 被误分类、批量层缺少待确认/停批决策。
- 定向 API 测试：20/20 通过，覆盖香蕉 406 单次恢复、连续 406 停止、标准结果断线待确认和下一任务切换通道。
- `npm test`：251/251 通过。
- 本轮没有使用真实 Key 发起付费请求；网络异常通过与现场一致的 `UND_ERR_SOCKET`、`ECONNRESET`、406 响应夹具验证。

## 经验教训

- 收到 HTTP 错误与没有收到 HTTP 响应是两类故障，不能共用网络切换策略。
- 明确的 406 表示本次请求已被拒绝，可做一次短延迟重试；连接重置无法确认服务端状态，绝不能照搬这一策略。
- 付费 POST 发出后的连接中断不能靠自动重试掩盖；没有服务商任务 ID 或幂等保证时，必须保留“不确定”状态。
- 备用网络通道用于后续任务恢复，不用于重复提交当前状态不明的任务。
