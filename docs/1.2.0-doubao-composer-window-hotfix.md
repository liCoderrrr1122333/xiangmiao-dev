# 1.2.0 豆包输入区与查看窗口热修

日期：2026-08-24

## 问题现象

1. 点击“查看豆包”后，专属 Chrome 虽然已启动，但不一定出现在耀创工坊窗口上方。
2. 豆包网页已登录、输入区可用且是新对话，AI 分析仍可能在发送前报错：“无法确认豆包输入区已经清空，本轮未发送。”
3. Gemini 仍处于适配阶段，但制作通道和分析来源继续显示为可点击选项，容易让用户误入不完整流程。

## 真实根因与证据

- 正式日志显示豆包页面为 `https://www.doubao.com/chat/`，`composerReady=true`、登录入口不可见、用户消息和助手回复均为 0，但清空门禁仍失败。这排除了未登录、旧对话和输入框缺失。
- 清空门禁过去把输入区附近所有 `img`、类名含 `upload` 或 `file` 的元素都当成附件。豆包空白输入区自身的上传入口和装饰图片因此被误计为残留附件。
- “查看豆包”先用 `background` 模式取得窗口，再尝试显示；缓存窗口也直接返回，没有先同步调用方要求的可见状态。
- Gemini 适配状态没有进入 Provider 按钮的可用性判断。

## 解决方式

- 新增独立的豆包输入区清洁策略，只把明确的附件卡片、文件卡片或“删除附件/移除附件”控件计为真实残留附件。
- 普通图片节点、上传入口和文件输入框不再阻止空白新对话发送；真实文本或真实附件卡片仍会阻止发送。
- 输入区清空时补发标准 `beforeinput`、`input` 和 `change` 事件；只有文本仍残留时进行一次有界二次清空，不增加发送补点。
- “查看豆包”明确请求 `visible` 模式；缓存窗口也会同步可见状态。Windows 原生显示链增加 `BringWindowToTop`，仍不设置永久置顶。
- 制作通道与分析来源的 Gemini 按钮统一灰显禁用，并通过 tooltip 说明“Gemini 适配中，暂不可用”。ChatGPT、豆包网页和耀创工坊专属 API 不受影响。

## 经验教训与边界

- 输入区清洁检查必须依赖明确的用户内容证据，不能把容器中的任何图片或上传类名都视为附件。
- “窗口已创建”和“窗口已在用户眼前”是两个状态；检查入口必须显式请求可见模式并验证原生窗口恢复。
- 当前环境没有持久 `js_repl`，视觉与 Electron 验证由仓库真实 Playwright/Electron 脚本完成。
- 本轮没有使用真实豆包账号发送分析消息，最终仍需 Hale 用最小单次 AI 分析和网感姿势手测确认豆包当天页面结构。
