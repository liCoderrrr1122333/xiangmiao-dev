# 1.1.5 完整相机成像与处理强度

日期：2026-08-24

## 现象

- 旧“批量降 AI 感”只有固定处理策略，无法根据不同图片控制处理力度。
- `camera-realism-code-only.zip` 的成像模拟包含更完整的镜头、光学、局部细节和胶片颗粒链路，当前实现只覆盖其中一部分。
- ZIP 原脚本使用固定随机种子；如果原样用于批量图片，会让不同图片带上重复的纹理模式。

## 根因

- 旧主进程处理器是针对首版功能的简化实现，参数没有抽象成可连续调节的成像配置。
- renderer 到主进程的请求契约没有强度字段，结果归档和外部文件夹两条批处理路径也无法共享同一强度。
- 如果直接嵌入 ZIP 的 Python CLI，会额外引入 Python/Pillow/NumPy/SciPy 运行时和发布体积，同时与应用现有 `sharp` 图像链路重复。

## 解决方式

- 将 ZIP 的主成像链路按等价阶段移植到 TypeScript + `sharp`：
  - 桶形镜头畸变与 RGB 增益。
  - 阴影/高光染色与对比度。
  - 宽尺度与细尺度两层局部细节。
  - 高光光晕、镜头暗角、色差、边缘模糊与边缘柔化。
  - 基于局部方差的单色/彩色颗粒，平坦区和暗部保留更真实的质感。
  - 随强度连续变化的 JPEG 质量与 4:2:0 色度采样。
- 保留 ZIP 的 `natural` 与 `aggressive` 参数作为强度 50 和 100 的锚点，增加中性锚点并连续插值。强度范围为 10–100，默认 50。
- 结果归档与导入文件夹共用同一强度；每张图片在主进程中使用独立随机种子，没有移植 ZIP 的固定种子。
- 在既有金色批处理窗口中增加“处理强度”滑块、数值和四档说明；处理进行时禁用滑块，避免同一批内参数漂移。
- 始终另存 JPG 副本，保持原始宽高，不覆盖原文件。ZIP 中需要人工手绘蒙版的可选局部修饰 CLI 没有重复嵌入此全图按钮；局部人脸处理继续由既有“批量面部自然化”独立负责。

## 经验教训与残余风险

- 处理强度表示成像处理力度，不是可量化的“AI 检测率”，不应承诺通过某个检测器。
- 强度 90–100 会有意放大色差、颗粒、压缩和明暗风格，可能损伤个别原图细节；默认 50 是更稳妥的起点。
- 完整成像算法处理整张图，不受红圈外保护约束；这是用户对“降 AI 感”的明确产品边界，且始终通过副本保留原图。
- 大图批处理继续使用顺序执行，避免多张高分辨率图片同时占用大量内存。
