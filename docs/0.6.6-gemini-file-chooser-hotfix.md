# 0.6.6 Gemini 原生文件选择框卡死热修复

日期：2026-08-10

## 发布范围

- 修复 Gemini 点击“上传文件”后弹出 Windows 原生“打开”窗口，导致自动化停在文件夹、无法继续写入提示词和发送的问题。
- 加强 Gemini 当前附件结构识别和新会话隔离，不改变 ChatGPT、项目格式、原图尺寸、红圈保护、参考图、提示词快照、并行任务、结果保存或断点续做协议。
- 保留专属 Chrome 登录目录和现有用户数据；本轮只生成安装包，不替 Hale 安装。

## 现象

1. Gemini 已进入做图页面并显示图片预览，但自动化点击附件菜单后弹出 Windows 原生“打开”窗口。
2. 文件窗口停留在桌面文件夹，程序不会自动选择文件，也不会继续粘贴提示词、发送请求或等待生成结果。
3. 运行日志显示前三次生成都停在“未确认完整接收附件”，第四次只有任务开始记录，与原生窗口阻塞时点一致。

## 根因

- 旧流程先点击 Gemini 的“上传文件”菜单项，再通过 CDP 查找隐藏文件输入并调用 `DOM.setFileInputFiles`。当前 Gemini 会在菜单点击时立即执行 `input.click()`，Windows 文件选择框因此早于 CDP 文件注入出现，并阻塞后续自动化。
- 原页面夹具只创建隐藏文件输入，没有真正调用 `input.click()`，所以过去的自动化测试没有复现原生窗口。
- Gemini 当前附件预览使用 `data-test-id="uploaded-img"`。旧识别逻辑偏向历史 `file-chip` 结构，同时把普通图片计入宽泛证据，既可能漏掉真实附件，也可能混入页面装饰图。
- 旧会话可能残留附件或生成状态；仅在原页面清理编辑器，无法保证下一项任务得到真正干净的新会话。
- 主流程设计为“附件确认后才写入提示词”，所以附件步骤被原生窗口卡住时，后面的复制、发送和出图都不会执行。

## 解决方式

- 在点击 Gemini 上传菜单之前调用 CDP `Page.setInterceptFileChooserDialog`，先拦截文件选择动作，再点击菜单、定位新文件输入并执行 `DOM.setFileInputFiles`；无论成功或失败都在 `finally` 中关闭拦截。
- 若当前 Chrome/CDP 不支持文件选择框拦截，则不冒险点击会弹出原生窗口的入口，转入既有 CDP 拖放后备路径。
- 将 `[data-test-id*="uploaded-img"]` 纳入附件快照、清理、等待和编辑器就绪判断，并把附件证据限定在当前编辑器区域。
- 移除把任意普通 `<img>` 当附件的宽泛计数，只接受当前附件容器及其已加载图片或画布证据。
- 分析、生成、重试和清理统一经过 `about:blank -> Gemini /app` 的新会话装载，同时继续保留 Google 登录、验证码和账号安全步骤的人工边界。
- 更新 Gemini 页面夹具，让“上传文件”真实执行 `input.click()`；新增残留 `uploaded-img` 清理回归和源码契约测试，确保以后再次出现页面改版时能在打包前暴露。

## 经验教训

- 网页文件上传不只是“找到 input 并写入路径”；必须控制触发 `input.click()` 的时序，否则原生窗口会先抢走自动化流程。
- 页面夹具必须复现真实事件链。只摆出 DOM 结构、不触发浏览器默认行为，会让关键回归出现假通过。
- 附件确认要识别当前页面的真实组件并限定在编辑器范围，不能用任意图片数量替代上传成功证据。
- 每个批次任务从明确的新会话开始，比依赖复杂的旧页面清理更可预测；但 OAuth 和账号安全边界仍必须由用户处理。
- 真实站点受网络地区限制时，应明确区分“代码回归通过”和“线上端到端未执行”，不能用历史成功或本地夹具冒充当前真实结果。
- 发布验收脚本若临时修改用户设置，结束时必须恢复原值并复核用户数据指纹。

## 残余风险
