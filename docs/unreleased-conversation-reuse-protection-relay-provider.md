# 1.1.5 未发布源码维护：会话复用、访问保护与中转站契约

日期：2026-08-24

状态：源码、本地验证和 Windows 安装包更新完成；版本保持 `1.1.5`，本轮未提交、未覆盖安装。

## 问题现象

1. ChatGPT 批量做图曾为每张任务建立新对话，重复触发页面导航、输入框重建和对话记录访问，增加了网页操作量与访问保护概率。
2. 访问保护冷却结束后会自动尝试恢复；保护尚未解除时，容易形成等待、探测、再次暂停的循环。用户关闭网页提示框后，软件也缺少独立的稳定恢复门禁。
3. 三路恢复阶段的界面仍可能展示用户原始并行数，而不是当前真正允许工作的通道数。
4. “中转站 API”此前只有 Provider 外壳和密钥存储：`protocolReady` 被硬编码为 `false`，连接测试不发送请求，正式做图在导出前直接终止；用户还需要手填 Base URL、模型和分辨率。

## 真实根因与证据

- 对话生命周期绑定在单张任务上，而不是绑定在通道上，因此批量任务产生了不必要的新对话操作。
- 保护状态把“冷却时间已到”近似当成“平台已经恢复”，缺少人工触发、页面稳定性检查和逐级恢复阶段。
- 并行状态只记录用户请求值，没有把保护暂停和恢复阶段映射为有效通道数。
- 连一连公开页面已给出固定 API 端点 `https://www.lianyilian.top`，并链接开源后端 `Wei-Shaw/sub2api`。该实现公开了 OpenAI 兼容的 `/v1/models`、`/v1/images/edits`、重复 `image` multipart 字段以及 URL/Base64 图片响应；原代码没有把这些协议接入现有 `RelayImageAdapter`。

## 解决方式

### 每通道复用 ChatGPT 对话

- 单路、二路、三路分别维护 1、2、3 个独立会话租约。
- 同一通道保存当前任务结果后，才在该会话发送下一张；每个会话完成 4 张后轮换，符合 3-5 张的控制范围。
- 每轮发送前保留 assistant 消息数、结果图片数、附件和发送基线，只接受基线后新增的回复与图片。
- 提示词明确要求只处理当前最新消息的附件，忽略会话内此前附件和编辑要求。
- 附件残留、结果归属不明、发送状态不确定、页面异常或访问保护会使租约失效；不确定发送状态禁止补点。
- AI 分析、网感姿势和正式做图继续使用相互隔离的会话用途，不共享附件上下文。
- 极简直传继续保持模型与思考强度查询、菜单扫描和点击均为 0。

### 访问保护与恢复

- 正常批量提交下限调整为 60 秒；发生保护后的恢复阶段下限为 120 秒。
- AI 分析、网感姿势和正式做图共用现有全局提交额度与页面操作队列。
- 保护出现后立即暂停新建对话、上传、发送、菜单、刷新和补点；已发送任务只读等待并保存，未发送任务保留断点。
- 冷却结束不再自动恢复；用户必须从软件发起一次“检查恢复”。网页“知道了”只关闭网页提示，不会清除软件保护状态。
- 恢复检查只读取保护提示、输入框和页面稳定状态，不负责点击“知道了”。确认健康后先恢复单路；连续成功 3 个任务后恢复二路，再连续成功 3 个任务后恢复用户请求的三路。
- 同一小时第一次保护冷却 5 分钟，第二次延长为 15 分钟，第三次停止自动倒计时并等待人工检查，避免循环恢复。
- UI 根据保护阶段显示 0、1、2 或 3 个实际有效通道，不再把用户选择值冒充当前执行值。

### 中转站 API Provider

- 新增 `createLianYiLianRelayTransport`，固定使用 `https://www.lianyilian.top`、`gpt-image-2`、`GET /v1/models` 和同步 `POST /v1/images/edits`。同步接口不依赖服务端对象存储，适合当前最小可靠接入。
- 正式做图一次性提交红圈主垫图、人脸参考图和穿搭参考图；支持重复 `image` multipart 字段、URL/Base64 结果、取消、下载和错误分类。
- 结果使用中转站独立的保真持久化：主垫图只在原始像素尺寸上补边，不提前缩小；服务返回后按同一映射逆向裁边，并以保持比例的方式归一到原图精确像素尺寸。服务原始结果逐字节保存在“中转站原始图”子目录，结果归档使用无损 PNG，不再执行横纵方向不同倍率的拉伸或强制 JPG 重编码。
- 1/2/3 路沿用现有并行设置。普通单张解析或保存失败不阻断其他任务；401/403 或 429 会停止批次并取消其余请求，避免无效 Key 或限流状态下继续消耗请求。
- Provider UI 调整为 ChatGPT、Gemini 和整行“中转站 API”；中转站选中后隐藏网页模型、思考强度、登录和窗口操作，固定显示“API / gpt-image-2 / 自动匹配原图”。配置状态文案同步收敛为“可使用 API 做图”。
- API Key 默认仅保存在当前进程内；勾选“记住本机”时使用 Electron `safeStorage` 加密，不进入普通设置、项目、断点、日志或错误通知。
- 配置窗口删除 Base URL、模型和分辨率输入，首次使用只需粘贴自己的 Key 并点击“保存并测试”；主界面只显示脱敏尾号。
- 未配置时禁止开始，中转站失败不会静默切换到 ChatGPT 或 Gemini。

### 中转站 `terminated` 响应中断热修

- 现场批次前 3 张已正常保存，第 4 张在约 5 分钟后只返回原始错误 `terminated`。脱敏日志中没有对应的中转站阶段记录，代码检查确认旧实现使用同步 `POST /v1/images/edits` 并要求把整张 PNG 以 `b64_json` 放进同一个长连接响应；响应头返回后，读取大体积响应体时连接被服务端、CDN 或网络层提前关闭，原始 `TypeError` 直接逃逸。因此这不是提示词、附件选择、图片保存或任务调度失败。
- 第一版热修曾优先尝试上游开源项目提供的 `POST /v1/images/edits/async`，但真实连一连部署返回 `404`。上游文档确认这通常表示服务端没有完整配置 `image_storage`，并非客户端可以补齐的对象存储能力。
- 后续 2 张双路现场日志确认：任务 1 在 `430ms` 内发生无 HTTP 响应的 `fetch failed`，任务 2 回落同步接口后在 `190554ms` 处读取响应中断；另一次尝试还明确返回当前 Key 分组未启用图片生成。上一版异步回落没有消除真实部署的同步长连接风险。
- 当前源码删除未启用异步端点的额外探测，固定使用已部署的 `POST /v1/images/edits`，并请求 `response_format=url`。服务端返回 URL 时只传输短 JSON，再单独下载图片；下载底层连接中断最多重试 1 次 GET，生成 POST 始终只提交一次，避免重复生成和扣费。
- `fetch failed` 现在展开脱敏后的标准底层原因，按阶段区分连接重置、DNS、拒绝连接、超时和 TLS；不再把所有网络故障压成同一句裸错误。
- 每个中转站批次启动前只执行一次 `/v1/models` 权限检查；模型列表没有 `gpt-image-2` 时在上传和创建结果预留前停止，明确提示用户修改 Key 分组。
- 新增脱敏任务阶段日志：开始、收到结果、保存完成和失败。只记录任务编号、通道、阶段、耗时、尺寸和错误分类，不记录 Key、提示词或图片内容。

### 中转站原图比例与无损输出热修

- 现场结果显示原图为 `1279x1706`，中转站返回 `1024x1536`。旧共享保存函数直接把宽度放大 `1.249` 倍、把高度放大 `1.111` 倍，因此人物横向被额外放宽约 `12.5%`；随后又统一编码为质量 96 的 JPG，文件从数 MB 降到数百 KB。
- 新实现不改写原图，也不把主垫图预先降采样。以 `1279x1706` 为例，只在原始像素上补成 `1279x1919` 的 2:3 临时画布，原图区域逐像素哈希保持一致。
- 服务结果按补边比例逆向裁剪，再使用等比 `cover` 归一到原图精确尺寸；`usedNonUniformStretch` 固定为 `false`。正式归档保存无损 PNG，服务返回的原始字节另行原子保存，二者均经过落盘校验。
- ChatGPT 与 Gemini 继续使用既有 JPG 保存路径；本次只分流中转站，避免改变两条已验证网页自动化链路。

## 验证边界与残余风险

- 本轮没有使用真实账号连续发送批量消息制造访问保护；保护、恢复和重复保护采用单元测试、页面夹具与故障注入验证。
- 当前不能证明平台访问保护可以被彻底消除；软件只减少不必要操作，并在保护出现后安全暂停和受控恢复。
- 中转站请求和响应使用本地 fetch 夹具验证，没有使用聊天中暴露过的旧 Key，也没有执行真实扣费图片生成。用户应撤销旧 Key，在软件中粘贴新 Key 后执行一次最小额度手测。
- 公开开源协议与连一连当前部署可能继续变化；如果服务商调整图片路径、模型名或字段，需要按其最新公开文档更新传输层。
- 连一连当前部署没有启用 sub2api 异步图片对象存储。当前源码请求 URL 结果，但服务端若忽略 `response_format=url` 并继续返回 Base64，服务端/CDN 的同步长连接仍是残余风险；要彻底消除只能由服务商启用其上游已经提供的 `image_storage` 异步任务能力。
- 持久 `js_repl` 启动 Electron 时遇到当前 Playwright 模块导出冲突，因此视觉检查由仓库内真实 Electron/Playwright 脚本完成；没有把页面夹具冒充真实服务端端到端验证。

## 经验教训

- 批量网页自动化的关键不是更快地点击，而是减少导航、复用稳定上下文，并让发送临界区只有一个所有者。
- 冷却时间结束只是允许检查，不代表平台已经恢复；恢复必须是显式、只读、单次并逐级放量的过程。
- 新 Provider 必须隔离状态、密钥和错误边界；公开协议只收敛到一个固定传输层，用户界面不应暴露无需选择的底层参数。
- 批处理必须区分单张失败与账号级失败；无效 Key 和 429 继续启动后续任务只会放大问题。
